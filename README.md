# QueOnline — ดูคิวออนไลน์

เว็บแอปสำหรับผู้ป่วยดูสถานะคิวโรงพยาบาลแบบเรียลไทม์บนมือถือ อ่านข้อมูลจากฐานข้อมูลระบบคิวเดิม
(`NUTZAA` / `Que_lcb` / ตาราง `Queue_q`) แบบ read-only

โปรเจกต์นี้แยกอิสระจาก AIAPRO ไม่ผูกกับ Klein Pro / ant-design-vue แต่เลือกใช้ **Vuetify 3** ทั้งระบบ (หน้าคิว +
หน้า Admin)

**หมายเหตุ (2026-08-31)**: วันนี้ทดลองสลับ UI library ของหน้าคิวผู้ป่วยหลายรอบตามคำสั่ง user แต่ละรอบ —
Vuetify 3 (เดิม) → ลอง Tailwind CSS 4 + reka-ui + motion-v (ย้อนกลับ ไม่สวยกว่า) → ลอง Vant 4 (ย้อนกลับอีกครั้ง —
user ส่งภาพหน้าจอ Vuetify เวอร์ชันก่อนหน้ามาระบุว่าสวยกว่า) → **กลับมาที่ Vuetify 3 ทั้งระบบ (ปัจจุบัน)** ระหว่างทาง
ย้อนกลับรอบล่าสุดยังเจอบั๊กจริงที่แก้ไปด้วย: การ์ดฉลอง "ถึงคิวแล้ว" (อิโมจิ+หัวข้อ+ข้อความ+chip) สูงพอที่จะทับกับ
ชื่อคนไข้/HN ด้านบนบนจอมือถือจริง (ความกว้างแคบ) แม้จะดูปกติในสกรีนช็อตจอกว้างก่อนหน้านี้ — แก้โดยลดขนาด/ย้าย
ตำแหน่งลง (`client/src/components/QueueStatusCard.vue` → `.lf-arrived`) รายละเอียดเต็มของทุกรอบอยู่ใน
`log/2026-08-31.md`

## โครงสร้าง

```
server/   ASP.NET Core 9 Web API (Dapper + Microsoft.Data.SqlClient) — อ่าน Queue_q แบบ read-only
client/   Vue 3 + Vite + Vuetify 3 — มือถือก่อน (mobile-first)
          2 "หน้า" แบบไม่ใช้ router (เช็ค pathname ตรงๆ ใน App.vue): "/" หน้าคิว, "/admin" หน้าตั้งค่า
```

## เริ่มต้นใช้งาน (dev)

**Backend**
```
cd server
dotnet run
```
ฟังที่ `http://localhost:5224` (ตาม `Properties/launchSettings.json`) ต้องมี
`server/appsettings.Development.json` (ไม่ commit เข้า git — ดูหัวข้อ "ความปลอดภัย" ด้านล่าง) พร้อม
connection string:
```json
{ "ConnectionStrings": { "QueDb": "Server=NUTZAA;Database=Que_lcb;User Id=...;Password=...;TrustServerCertificate=True;Encrypt=True" } }
```

**Frontend**
```
cd client
npm install
npm run dev
```
เปิด `http://localhost:5173` (หรือพอร์ตถัดไปถ้าพอร์ตนี้ถูกใช้อยู่แล้ว) — ปรับ `client/.env.development`
(`VITE_API_BASE_URL`) ให้ตรงพอร์ต backend จริง และปรับ `Cors:AllowedOrigins` ใน `server/appsettings.json`
ให้ตรงพอร์ต frontend จริงด้วย

## หน้าจอ

**เหลือหน้าเดียว** (`/`) — ตามที่ตกลงกัน: ผู้ป่วยไม่จำเป็นต้องเห็นรายชื่อคิวทั้งหมดของคนอื่น เห็นแค่ของตัวเองพอ

- **ยังไม่รู้คิวตัวเอง** (ไม่มี query param): หน้าทักทาย — โลโก้/ชื่อ รพ. + คำทักทาย + ช่องกรอกหมายเลขคิว
  (ตั้งชื่อ "โรงพยาบาลวิภาราม" ไว้แล้ว แก้ต่อได้จากหน้า `/admin` โดยไม่ต้องแก้โค้ด — ดูหัวข้อถัดไป)
- **รู้คิวแล้ว** (ผ่าน query param หรือกรอกในช่อง): หมายเลขคิวของท่านตัวใหญ่ + **เลขคิวปัจจุบัน** (คิวล่าสุดที่ถูกเรียก
  ในกลุ่มเดียวกันวันนี้) กับ **จำนวนคิวรอ** เป็น 2 กล่องคู่กัน + กล่อง **ระยะเวลารอโดยประมาณ** + timeline
  ตามจุดบริการจริงที่มีข้อมูล (ไม่ใช่รายการคิวคนอื่นทั้งหมด) — ดีไซน์อ้างอิงจากภาพตัวอย่างแอป "HiNav" ของ
  รพ.วารินชำราบที่ผู้ใช้ส่งมา

### จับสีตามภาพตัวอย่างจริง — โทนน้ำเงินเข้ม + ส้ม (2026-08-31)

หลังทำโครงหน้าตามภาพ HiNav แล้ว ผู้ใช้ขอให้จับ "สีสัน" ให้เหมือนภาพตัวอย่างด้วย ไม่ใช่แค่โครง — เพิ่มโทน 2 สีแยกบทบาท
กันชัดเจน แทนที่จะใช้สีเดียว (`primaryColor`) ทาทุกอย่างเหมือนเดิม:

- **`primaryColor`** (น้ำเงินเข้ม) — ชื่อ รพ. ในหัว, ปุ่ม, ค่าตัวเลขในกล่องสถิติ (เลขคิวปัจจุบัน/จำนวนคิวรอ),
  แถบสรุปด้านล่างการ์ด (footer bar สีทึบตัวอักษรขาว ตามภาพตัวอย่าง)
- **`accentColor`** (ส้ม-แดง ค่าเริ่มต้น `#e8542a`) — ตัวเลขคิวใหญ่ตรงกลาง, กล่อง "ระยะเวลารอโดยประมาณ" (พื้นหลัง
  โทนส้มอ่อน + ตัวเลขสีส้ม), ไอคอนวงกลมทึบของขั้นตอนที่ "กำลังดำเนินการอยู่" ใน timeline

ทั้งสองสีตั้งแยกกันได้จากหน้า `/admin` (เพิ่มช่อง "สีเน้น" คู่กับ "สีธีมหลัก" เดิม) ส่วนหัวเปลี่ยนจาก banner gradient
สีน้ำเงินเต็มจอ (ดีไซน์รอบก่อน) เป็นแถบขาวสะอาดแบบภาพตัวอย่าง ชื่อ รพ. เป็นตัวหนังสือสีน้ำเงินแทนตัวขาวบนพื้นสี

เพิ่ม timeline 3 สถานะ (ของเดิมมีแค่ 2: เสร็จแล้ว/ยังไม่ถึง) — ขั้นตอนแรกที่ยังไม่เสร็จจะไฮไลต์เป็นวงกลมสีส้มทึบ
("กำลังดำเนินการอยู่") ต่างจากขั้นตอนที่เหลือซึ่งเป็นวงกลมโปร่งสีเทา (ยังไม่ถึง) ตรงตามภาพตัวอย่างที่ขั้น "ซักประวัติ"
มีวงกลมส้มต่างจากขั้นถัดไป

### ย่อ spacing ให้พอดี 1 หน้าจอ ไม่ต้องเลื่อน (2026-08-31)

หน้าสถานะ (โดยเฉพาะตอน "รอเรียก" ที่มีกล่องสถิติ + กล่องเวลารอ + timeline + แถบสรุป ครบทุกส่วน) เดิมสูงเกิน
มือถือจอเล็กจนต้องเลื่อนดู — ปรับให้พอดี **1 หน้าจอพอดี ไม่ต้องเลื่อนเลย** (ทดสอบแล้วที่ viewport 338×600:
`scrollHeight === clientHeight` ทั้ง 3 สถานะ — หน้าทักทาย, รอเรียก, ถึงคิวแล้ว):

- `.hero` เปลี่ยนเป็น `min-height: 100dvh` (ใช้ dynamic viewport height แม่นกว่า `100vh` บนมือถือที่มี
  แถบที่อยู่/แถบเครื่องมือของเบราว์เซอร์เปลี่ยนขนาดได้) + `display:flex; flex-direction:column` ให้ส่วนหัวคงที่
  ด้านบน ส่วนเนื้อหายืด/หดตามพื้นที่ที่เหลือ (`content-container { flex:1 }`)
  - **`100dvh` ต้องใช้ browser เวอร์ชันใหม่พอสมควร** (Chrome/Edge/Safari ปี 2023+, Android WebView รุ่นใหม่) —
    เบราว์เซอร์เก่ามากจะไม่รู้จัก `dvh` แล้ว fallback เป็นค่า default ของเบราว์เซอร์ (ปกติจะ fallback ไม่พังแค่
    ไม่แม่นเท่า) ยังไม่ได้ทดสอบกับเบราว์เซอร์เก่ามากๆ
- ลด padding/margin ทุกจุดในการ์ด (จาก `pa-6` เหลือ `pa-3`, จาก `my-5`/`mt-4` เหลือ `my-2`/`mt-1` ฯลฯ) และลด
  font-size ตัวเลขคิวใหญ่ (`clamp(3rem,16vw,4.5rem)` → `clamp(2.25rem,12vw,3.25rem)`)
- **ถ้าจอเล็กมากจริงๆ หรือผู้ใช้ตั้ง "ขนาดตัวอักษร" เป็น "ใหญ่" ในหน้า admin** เนื้อหาอาจยังล้นจอได้ — จงใจไม่ใส่
  `overflow: hidden` บังคับตัด เพราะการซ่อนข้อมูลสำคัญ (เช่นแถบสรุปด้านล่าง) แย่กว่าการให้เลื่อนดูได้ในกรณีขอบๆ
  แบบนี้ ถือเป็น graceful degradation ไม่ใช่ fit แบบตายตัว 100%

### เลขคิวปัจจุบัน / เวลารอโดยประมาณ (2026-08-31)

สองค่านี้คำนวณจาก **ข้อมูลเวลาเรียกคิวจริงของวันนี้** ไม่ใช่ตัวเลขสุ่มหรือคงที่:

- **เลขคิวปัจจุบัน** (`currentServingNumber`) = คิวที่มี `qtimecall` ล่าสุดในกลุ่มเดียวกันวันนี้
- **เวลารอโดยประมาณ** (`estimatedWaitMinutes`) = ค่าเฉลี่ยช่วงเวลาระหว่างการเรียกคิวแต่ละครั้งจริงวันนี้ (นาที) ×
  จำนวนคิวที่รออยู่ก่อนหน้า — ต้องมีการเรียกคิวจริงอย่างน้อย 2 ครั้งวันนี้ (สร้างช่วงเวลาได้อย่างน้อย 1 ช่วง) ถึงจะ
  แสดงตัวเลขได้ ถ้าน้อยกว่านั้นจะขึ้น "ยังไม่มีข้อมูลเพียงพอสำหรับประมาณเวลาวันนี้" ตรงๆ **ไม่เดาตัวเลขให้** —
  โค้ดคำนวณอยู่ที่ `server/Models/QueueTimeFormat.cs` → `QueueWaitEstimate.Compute`, เรียกใช้จาก
  `QueueRepository`/`RegistrationQueueRepository` ทั้งสองฝั่ง (คลินิก/ลงทะเบียน)
- จำนวนช่วงเวลาที่ใช้คำนวณ (`estimatedWaitSampleSize`) แสดงกำกับไว้ด้วยเสมอ ("อ้างอิงเวลาเรียกคิวจริงวันนี้ N ช่วง")
  เพื่อความโปร่งใสว่าตัวเลขนี้แม่นแค่ไหน (N น้อย = ค่าเฉลี่ยยังไม่นิ่ง)

### บั๊กที่เจอระหว่างทำ: Vue Transition ค้างตอนสแกน QR (แก้แล้ว)

`<Transition mode="out-in" appear>` ที่ใช้สลับหน้าทักทาย↔สถานะ ถ้าเปิดด้วย query param (สแกน QR) ที่ทำให้ระบบ
สลับจากหน้าทักทายไปหน้าสถานะเกือบจะทันทีหลังโหลดหน้า (เร็วกว่า enter transition ของหน้าทักทายเองจะเล่นจบ) จะไป
ชนกับ animation "appear" ตอนโหลดครั้งแรก ทำให้ transition ค้างกลางทาง (หน้าทักทายไม่หายไป หน้าสถานะไม่โผล่มา
ทั้งที่ state ข้างในถูกต้องทุกอย่าง) — แก้โดยปิด `appear` เฉพาะตอนมี query param `q`/`ocm` ตั้งแต่แรก (คำนวณแบบ
sync ก่อน mount) เพราะกรณีนั้นรู้อยู่แล้วว่าจะสลับหน้าทันที ไม่จำเป็นต้องมี appear animation ให้ชนกันตั้งแต่ต้น

### เข้าคิวตรงผ่าน QR code (สแกนแล้วเห็นคิวตัวเองทันที)

หน้าเดียวนี้อ่าน query string ตอนโหลดหน้า — ถ้าตั๋วคิวที่ปริ้นออกมามี QR code ชี้มาที่ URL รูปแบบนี้ แอปจะข้าม
หน้าทักทาย/ฟอร์มไปเลย เปิดมาเห็นสถานะคิวตัวเองทันที:

```
https://<โดเมนที่ deploy>/?q=<หมายเลขคิว>     เช่น  /?q=A5
https://<โดเมนที่ deploy>/?hn=<เลข HN>        ค้นด้วยเลข HN (qocmchatnum) แทนหมายเลขคิวก็ได้
```

การสร้าง QR code ที่ปริ้นบนตั๋วคิวจริง (ต่อเข้ากับเครื่องปริ้นตั๋ว/ระบบออกบัตรคิวเดิม) เป็นงานอีกฝั่งที่ยังไม่ได้ทำในนี้ —
โค้ดฝั่งเว็บพร้อมรับ URL รูปแบบข้างต้นแล้ว เหลือแค่ทีมที่ดูแลเครื่องปริ้นตั๋วเข้ารหัส URL นี้ลง QR ให้ตรงกับ
หมายเลขคิวที่ออกจริง

### หน้า Admin (`/admin`) — แก้ชื่อ/โลโก้/สี/เสียง/ข้อความ โดยไม่ต้องแก้โค้ด

รหัสผ่านเดียว ไม่มีระบบ user (`server/Data/AdminSessionStore.cs` — token เก็บใน memory, หมดอายุ 12 ชม.
หรือ API restart ก็ต้องล็อกอินใหม่ ยอมรับได้เพราะเป็นแค่หน้าตั้งค่า ไม่ใช่ระบบที่มีความเสี่ยงสูง) แก้ไขได้:

- ชื่อโรงพยาบาล, tagline, คำทักทายหน้าแรก
- ข้อความตอน "ถึงคิวแล้ว" (หัวข้อ + ข้อความรอง) — ใช้ทั้งใน toast/push notification ด้วย ไม่ใช่แค่หน้าจอ
- ฟอนต์ เลือกได้ 4 แบบ (`client/src/config/fonts.js` → `FONT_OPTIONS`: IBM Plex Sans Thai/Sarabun/Kanit/
  Noto Sans Thai ทุกตัวฝังในโปรเจกต์ ไม่โหลดจาก CDN)

### การแจ้งเตือนเมื่อใกล้ถึงคิว

หน้าเดียวนี้ (`client/src/composables/useQueueAlert.js`) โพลผลลัพธ์ทุก 10 วิ แล้วแจ้งเตือน
ผู้ป่วยอัตโนมัติ 3 ระดับตามที่ตกลงกัน — **อีก 2 คิวจะถึงคิวของท่าน → อีก 1 คิวจะถึงคิวของท่าน → ถึงคิวของท่านแล้ว**
(ระดับ "ถึงคิวแล้ว" อิงจาก timeline step `call` ว่าถูกเรียกจริงหรือยัง ไม่ได้อิงจาก `aheadCount === 0` เฉยๆ
เพราะ "ไม่มีใครรออยู่ก่อนหน้า" กับ "ถูกเรียกแล้ว" เป็นคนละสถานะ) แต่ละระดับแจ้งครั้งเดียวต่อการค้นหาหนึ่งครั้ง
(รีเซ็ตเมื่อกดค้นหาใหม่) และถ้าคิวข้ามระดับไปเลย (เช่นเรียกพร้อมกันหลายคิวจนอีกฝ่าย aheadCount กระโดดจาก 5 เป็น 0)
จะแจ้งแค่ระดับล่าสุดที่เร่งด่วนที่สุด ไม่แจ้งซ้อนของเก่า

ช่องทางแจ้งเตือนที่ใช้ตอนหน้าเว็บยังเปิดอยู่ (foreground/background tab, ยังไม่ปิด):
- เสียงชิม (chime) สังเคราะห์ด้วย Web Audio API 2 แบบ — เสียง "ติ๊ง-ต่อง" นุ่มๆ (สองโน้ตไล่เสียงขึ้น) สำหรับแจ้งอีก
  2/1 คิว, เสียง "ติ๊งติ๊งติ๊ง" 3 โน้ตรื่นหูกว่าสำหรับตอนถึงคิวแล้ว (ให้รู้สึกเร่งด่วน/ยินดีกว่าแบบเดิม) — สร้างเสียงเอง
  ไม่มีไฟล์เสียงภายนอกให้โหลด (`client/src/composables/useQueueAlert.js` → `playChime`)
- สั่นเครื่อง (`navigator.vibrate`, มือถือ Android เท่านั้น — iOS Safari ไม่รองรับ)
- Browser Notification ทันที (ต้องขอสิทธิ์ก่อนผ่านลิงก์ "เปิดการแจ้งเตือนขณะเปิดหน้านี้ไว้" — เป็น user gesture
  บังคับของเบราว์เซอร์)
- Banner สีเน้นในหน้าเว็บเองเสมอ (ทำงานได้แม้ผู้ใช้ไม่ให้สิทธิ์ notification)

### Push Notification เต็มรูปแบบ (ใช้ได้แม้ปิดแท็บ/ปิดแอป)

นอกจากด้านบน มีปุ่ม **"แจ้งเตือนแม้ปิดแอป"** (โผล่หลังค้นหาเจอคิว ก่อนคิวจะถึง) ที่เปิดใช้ Web Push จริง —
เซิร์ฟเวอร์จะยังคอยเช็คคิวและส่งแจ้งเตือนให้แม้ผู้ป่วยปิดแท็บ/ปิดเบราว์เซอร์ไปแล้ว (ยกเว้นถอนการติดตั้งเบราว์เซอร์หรือปิดเครื่อง)
— หมายเหตุ: เสียงแจ้งเตือนของ push notification ใช้เสียง default ของระบบปฏิบัติการ ไม่สามารถปรับเป็นเสียง chime
ที่ custom ได้เหมือนตอนหน้าเว็บเปิดอยู่ (ข้อจำกัดของ Web Push API เอง ทุกเว็บแอปเจอเหมือนกัน)

**สถาปัตยกรรม**:
- `client/public/sw.js` — Service Worker รับ event `push` แล้วเรียก `showNotification()`, รองรับ `notificationclick`
  เพื่อโฟกัสกลับมาที่แท็บเดิม
- `client/src/composables/usePushSubscription.js` — ขอสิทธิ์ notification → ลงทะเบียน service worker →
  `pushManager.subscribe()` ด้วย VAPID public key จาก `GET /api/push/public-key` → ส่ง subscription + เป้าหมายที่ติดตาม
  (hn/qnumber) ไปเก็บที่ backend ผ่าน `POST /api/push/subscribe`
- `server/Data/PushSubscriptionStore.cs` — เก็บ subscription ใน **SQLite แยกไฟล์ต่างหาก**
  (`server/App_Data/push_subscriptions.db`, gitignored) **ไม่แตะฐาน `Que_lcb` ของโรงพยาบาลเลย** เพราะแอปนี้อ่าน
  Queue_q แบบ read-only เท่านั้น การเก็บ state ของแอปตัวเองควรแยกจากฐานข้อมูลระบบคิวเดิมเสมอ
- `server/Services/QueueAlertBackgroundService.cs` — `BackgroundService` วน poll ทุก subscription ทุก 10 วิ
  (จังหวะเดียวกับที่ frontend poll) ด้วย logic ระดับการแจ้งเตือนชุดเดียวกับ `useQueueAlert.js`
  (`server/Models/WebPushOptions.cs` → `QueueAlertLevel`) เมื่อระดับเปลี่ยนจะเข้ารหัสและส่งผ่าน `WebPush` NuGet
  package (Web Push Protocol มาตรฐาน RFC 8291/8292) ระดับ "ถึงคิวแล้ว" เป็น one-shot — ส่งเสร็จแล้วลบ subscription
  ทิ้งอัตโนมัติ (ไม่ต้องแจ้งซ้ำ) subscription ที่ browser ยกเลิกไปแล้ว (push service ตอบ 404/410) หรือคิว/เลข HN
  ไม่พบในวันนั้น (ข้ามวันแล้ว) จะถูกลบทิ้งอัตโนมัติเช่นกัน — ไม่มี subscription ค้างสะสมไม่รู้จบ

**VAPID keys**: public key อยู่ใน `server/appsettings.json` (`WebPush:PublicKey`, ไม่ใช่ความลับ) private key
อยู่ใน `server/appsettings.Development.json` เท่านั้น (gitignored) — คู่ที่ใช้ตอนนี้เป็น key **สำหรับ dev เท่านั้น**
สร้างด้วย `npx web-push generate-vapid-keys`, ก่อนขึ้น production ต้องสร้างคู่ใหม่แล้วเก็บ private key เป็นความลับ
จริงจัง (env var/secret manager) และเปลี่ยน `WebPush:Subject` จาก `mailto:admin@queonline.local` เป็นอีเมลติดต่อจริง

**ทดสอบแล้ว (2026-08-29)**: subscribe จริงผ่านเบราว์เซอร์ → backend เก็บ subscription → background service ตรวจพบ
ระดับ "อีก 1 คิว" → เข้ารหัส payload และส่งผ่าน Web Push protocol สำเร็จ (log: `Push sent to subscription 1: อีก 1
คิวจะถึงคิวของท่าน`, ไม่มี error จาก push service) — ยืนยันได้ว่า pipeline ทั้งสายทำงานถูกต้องจนถึงขั้น push service
ยอมรับข้อความ **แต่ยังไม่สามารถยืนยันขั้นสุดท้ายว่ามือถือ/เบราว์เซอร์จริงเด้ง notification ให้เห็นหรือไม่** เพราะ
สภาพแวดล้อมทดสอบอัตโนมัติ (Chrome ที่ควบคุมผ่าน automation) ไม่มีการยืนยันว่าเชื่อมต่อกับ push service ของ Google
(FCM) แบบสมบูรณ์เหมือนเบราว์เซอร์จริงบนมือถือ — **แนะนำให้ทดสอบบนมือถือ/เบราว์เซอร์จริงอีกครั้งก่อนใช้งานจริง**
เพื่อยืนยันขั้นตอนสุดท้ายนี้

## หมายเหตุสำคัญเกี่ยวกับข้อมูล

**Field mapping ยืนยันโดยโรงพยาบาลแล้ว (2026-08-31)** — แทนที่ของเดิมที่เคยอนุมานผิดจาก stored procedure:

- เวลาลงทะเบียน = `qdatetime` (**ไม่ใช่** `qtimeregister` ที่ stored procedure เดิมใช้แต่ไม่ตรงกับที่แอปนี้ควรอ่าน)
- HN ของคนไข้ = `qocmchatnum` (**ไม่ใช่** `qocmnum` ซึ่งเป็น internal id คนละตัว)
- เลข visit = `qocmVst`
- `qstatus` มีแค่ 4 ค่า: `S`=ใหม่, `L`=แล็ป, `F`=การเงิน, `P`=ห้องยา — แมปเป็นภาษาไทยใน
  `server/Models/QueueTimeFormat.cs` (`QueueStatusLabel`) ค่าที่ไม่รู้จักจะแสดงค่าดิบแทน ไม่ซ่อนไว้เฉยๆ

รายละเอียดอื่นที่ยังอนุมานจาก stored procedure เดิม (`StGetQueData_Display`, `GetQuecall`,
`GetQuecallfin/lab/pha`):

- คอลัมน์เวลาทั้งหมด (`qtimecall`, `qtimecalllab`, `qtimecallfin`, `qtimecallpha`, `qdatetime`)
  เป็น `varchar` เก็บรูปแบบ `yyyyMMddHHmmss` (ไม่มี CHECK constraint บังคับ) — พาร์สใน
  `server/Models/QueueTimeFormat.cs`, ถ้าพาร์สไม่ได้จะคืนค่า `null` แทนที่จะ throw (พบข้อมูลทดสอบที่ผู้ใช้ใส่ตรง
  เข้า DB เองมีรูปแบบสั้นกว่า 14 หลัก เช่น `20260831` + เลขลำดับ 4 หลัก — พาร์สไม่ได้ตามคาด แต่ระบบไม่ error
  แค่แสดงเวลาไม่ได้ ส่วน "ทำแล้วหรือยัง" ของขั้นตอนนั้นยังถูกต้องเพราะเช็คแยกจากการพาร์สเวลา)
- **บั๊กที่เจอจากการทดสอบ (2026-08-31, แก้แล้ว)**: ข้อมูลทดสอบที่ใส่ตรงเข้า `Queue_q` (ไม่ผ่านแอปคิวเดิม) มีคอลัมน์
  เวลาเป็น **empty string (`''`) ไม่ใช่ NULL จริง** เมื่อยังไม่เกิดขั้นตอนนั้น — โค้ดเดิมเช็คแค่
  `column is not null` (C#) / `IS NOT NULL` (SQL) ซึ่ง `''` ก็ถือว่า "not null" ทำให้ขั้นตอนที่ยังไม่เกิดขึ้นจริง
  (เช่น "เรียกเข้าห้องตรวจ") ขึ้นสถานะ "เสร็จแล้ว" ผิดๆ แก้โดยเพิ่ม `QueueTimeFormat.HasValue()` (เช็คทั้ง null และ
  empty/whitespace) แล้วเปลี่ยนทุกจุดที่เคยเช็ค `is not null` ตรงๆ ให้เรียกผ่านนี้แทน (`QueueRepository.cs`) —
  ฝั่ง SQL ก็ต้องเติม `AND col <> ''` คู่กับ `IS NOT NULL` เสมอ ไม่พอแค่ `IS NOT NULL` อย่างเดียว **ถ้าเจอ column
  เวลาตัวใหม่ในอนาคต ต้องระวังจุดนี้ด้วยเช่นกัน**
- Timeline ในหน้า "คิวของฉัน" **ไม่ได้อ้างอิง `qstatus` โดยตรง** แต่ดูจากว่าคอลัมน์เวลาแต่ละขั้นตอนมีค่าหรือไม่
  (แข็งแรงกว่าเพราะไม่ขึ้นกับความหมาย status code ที่ยังไม่ชัดเจน 100%)
- `Queue_q.qdep` ผูกกับ `MasterGroup.depid` แบบ `LEFT(qdep, LEN(depid))` (เช่น `qdep='A01'` จับคู่กับ
  `depid='A'`) — คัดลอก logic นี้มาจาก `StGetQueData_Display`/`GetQuecall` ตรงๆ
- ยังไม่ได้เชื่อมกับ `HIS_*` (ฐานข้อมูลโรงพยาบาลหลัก ผ่าน linked server) เพราะ query ในระบบเดิมที่อ้างถึงต้อง
  ใช้ cross-database join ที่ dev environment นี้ไม่มีสิทธิ์เข้าถึง — ใช้ `Cache_OcmInf`/`MasterDep`/`MasterGroup`
  ในฐาน `Que_lcb` เองแทน ซึ่งครอบคลุมชื่อคนไข้/แผนกที่ต้องแสดงผลแล้ว

## ความปลอดภัย

- `server/appsettings.Development.json` มี connection string จริง (user/password) — อยู่ใน `.gitignore` แล้ว
  **ห้าม commit ไฟล์นี้เข้า git**

- `/api/admin/*` (แก้ branding/สี/เสียง, เขียนแค่ SQLite ของแอปเอง ไม่แตะ Que_lcb) มี authentication ด้วยรหัสผ่านเดียว
  — รหัสผ่านตอนนี้คือ `Admin@123` (`server/appsettings.Development.json` → `Admin:Password`) เป็นรหัสง่าย
  **แนะนำให้เปลี่ยนเป็นรหัสที่คาดเดายากกว่านี้ก่อนขึ้นใช้งานจริงเช่นเดียวกับรหัส SQL** และห้าม deploy โดยไม่ตั้งค่านี้
